# Design: Build-time manifest injection

Status: implemented · Scope: `contributes.snippets` in `package.json`
Related: [build-trace.md](build-trace.md) (same "generated artifacts are not source" principle)

## The problem

`contributes.snippets` is a list of `.snippets/*.json` paths:

```json
{ "language": "postscript", "path": ".snippets/Arithmetic and Math Operators.json" }
```

Those files are generated by `scripts/snippetsGenerator.ts` from the headings of
`Operators.md`, plus one merged file for `snippets/*.json`. They are produced
artifacts and are not tracked by git, so the manifest that lists them is a
**derived value**: tracking it in git would mean a second, hand-maintained copy
of the same list, kept in sync with a generator by discipline alone.

But `vsce` only reads `package.json` when packaging, so the field must physically
exist in the file at that moment. That leaves one option: inject it while
packaging and remove it afterwards.

## Where the injection point belongs (and where it does not)

Injection runs in `postbuild` (`npm run build` → `npm run build:snippets`).
A seemingly cleaner alternative — generate only from `prepackage` so that a plain
build never touches the manifest — was evaluated and **rejected**:

1. **Development parity.** `npm run watch` has `prewatch → build`. The Extension
   Development Host loads `package.json`; without the field, native snippet
   completion is missing during development and only appears in the shipped
   package. That is a difference users would find before we would.
2. **One build path.** `prepackage` is already `clean:out && build`, so moving
   the injection would not remove a single write — it would only wrap the write
   in an `if (packaging)` branch, making local and CI builds take different code
   paths. Reproducibility is worth more than a tidy `git status`.
3. **Same category as `out/`.** The manifest registers generated files, exactly
   like esbuild writing `out/`. It is build output that happens to live in a
   tracked file, not source.

## Failure safety

npm does not run `post<script>` when the main script fails (verified: a failing
`exit 3` script leaves `postx` unexecuted), and Ctrl-C behaves the same way.
`vsce package` fails in routine situations — bad `--out` directory, unreadable
file, network during `publish` — and those are precisely the moments when a
leftover field would be committed by accident.

So packaging goes through `scripts/vsceRun.ts` instead of `postpackage`:

- spawns the real `vsce` (resolved from `node_modules`, run with the current node
  binary, no PATH assumptions), forwards args and exit code;
- restores the manifest in `finally`-like fashion on child exit, spawn error,
  `SIGINT`, `SIGTERM`, and `process.on('exit')`;
- `npm run clean` also restores, since "clean" should leave no generated state;
- `npm run restore:manifest` is the manual escape hatch.

`scripts/manifest.ts` holds the single implementation: idempotent (a missing
field is a no-op), byte-stable (skips the write when the serialized result is
already identical, keeps the trailing newline).

## Line endings

`package.json` is rewritten by Node, which always emits LF, while
`* text=auto` + `core.autocrlf=true` made the Windows working copy CRLF. Every
build therefore flipped the file's line endings (invisible in `git diff`, but
enough to break `git diff --exit-code` in CI and to produce a warning on every
run). `.gitattributes` now pins `package.json text eol=lf`.

## Verification

- Byte-level closure: `cp package.json` → `npm run build` (field injected) →
  `npm run restore:manifest` → `cmp` reports no difference.
- Success path: `npm run package` → 41 files, field removed, `git diff` clean.
- Failure path: `npm run package -- --out /nonexistent-dir/x.vsix` → exit 1,
  field still removed.
- CI asserts both halves: the committed manifest must not contain the field, and
  the working copy must match its tracked state after packaging.
